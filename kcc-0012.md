## Abstract

This document specifies how a browser wallet exposes a **provider** object to a
web application (app). It also specifies how an app discovers every provider
that is present in a page. The provider has one `request` method that carries
named remote procedure calls. The provider also has an event emitter that
reports changes of connectivity, network, and account. Discovery uses `window`
events. With these events, any number of wallets can coexist without a shared
global variable.

The design mirrors the EIP-1193 provider interface and the EIP-6963 discovery
protocol of Ethereum. It adopts their conventions for method names,
authorization, permission, and errors. It adapts them to Kaspa with network
identifiers, prefixed addresses, sompi amounts, and
[KIP-5](https://github.com/kaspanet/kips/blob/24db7104f1b52f5c77781f93af6ace0fddf8e80f/kip-0005.md)
message signatures. The adaptation also includes a transaction signing method.
With this method, an app builds a transaction that can include inputs that
covenants authorize. The wallet signs only the inputs that it controls.

## Motivation

Several Kaspa browser wallets inject their own global objects. Each wallet has
its own method names, spellings of the network identifier, and event names. An
app that wants to support all of them carries one adapter per wallet. A new
wallet gains support only when every app adds one more adapter.

Ethereum had the same problem before EIP-1193 and EIP-6963. EIP-1193 gave
every wallet the same provider shape. EIP-6963 replaced the single
`window.ethereum` global with an event-based protocol for announcements. With
that global, each wallet overwrote the value, so only the last wallet to write
it remained visible.

The reuse of the conventions of Ethereum, instead of new ones, has two
benefits. Developers who come from EVM tooling immediately recognize
`request`, `accountsChanged`, error code `4001`, and
`wallet_requestPermissions`. Years of production use settled the tradeoffs
behind those conventions.

Covenant transactions add one requirement that the API of Ethereum does not
have. Some apps build a transaction with inputs that on-chain rules authorize,
for example a token covenant that [KCC-20](kcc-0020.md) defines. Such an app
needs a wallet that signs only the user's own inputs and leaves every other
input unchanged. This document specifies that signing mode as an addition.

### 1. Definitions

The list below gives the terms in the order of the execution chain that they
describe. An app calls a provider. A wallet exposes the provider. The wallet
communicates with a remote.

- **Web application** or **app**: Code that runs in a browsing context and
  consumes a provider.
- **Provider**: A JavaScript object that is available to an app. The object
  gives the app access to Kaspa through a wallet.
- **Wallet**: An end-user application that manages private keys, performs
  signing operations, and mediates between the provider and a remote. In
  this document, a wallet is typically a browser extension. The interface
  does not depend on that.
- **Remote**: An endpoint that services the requests that a wallet forwards
  to it. The endpoint is typically a Kaspa node.
- **Origin**: The origin of the browsing context that exposes the provider, as
  the HTML specification defines it (scheme, host, and port).
- **Account**: The set of addresses a wallet spends as one balance. The set
  MAY contain one address. A wallet that spends one address has an account
  whose only address is that address. The set MAY also contain every address
  the wallet derives for one balance, including receive addresses and change
  addresses, and including addresses the wallet has not disclosed. A wallet
  MUST NOT place one address in two accounts. A second balance is a second
  account. A wallet MAY hold several accounts and MAY authorize more than one
  of them for one origin. The provider MUST NOT return an extended public
  key, a derivation path, or any other value from which an app can derive an
  address.
- **Disclosed address**: An address of an authorized account that
  `kaspa_accounts` returns. The user chooses which accounts to authorize and
  which addresses of those accounts to disclose. The wallet MUST NOT disclose
  an address of an account the user did not authorize.
- **Watch-only account**: An account for which the wallet can derive
  addresses and cannot produce a signature. The wallet MAY authorize it. A
  method that needs a signature from it is rejected as in
  [Section 5.4](#54-watch-only-accounts).
- **Active disclosed address**: The first element of the array that
  `kaspa_accounts` returns, when that array is not empty. When an app does
  not name an address, the account that contains this element is the account
  the app is using. Every disclosed address is authorized. An app MUST NOT
  require the user to change the wallet's selection to use a disclosed
  address. An app MUST NOT treat the absence of an address from this array
  as proof that an authorized account holds no further funds.
- **Network identifier**: The string that names a Kaspa network, defined in
  [Section 2](#2-network-identifiers). This document carries it in a field
  named `networkId`.
- **RPC method**: A named procedure that `request` carries.
- **Restricted method**: An RPC method that requires prior authorization of
  the origin, defined in [Section 5](#5-authorization).

### 2. Network Identifiers

A network identifier is the string form of the network id of a Kaspa node.
The ABNF grammar (RFC 5234) of the identifier is:

```text
network-id   = "mainnet" / "devnet" / "simnet" / testnet-id
testnet-id   = "testnet-" suffix
suffix       = %x31-39 *DIGIT          ; decimal, no leading zeros
```

Only a `testnet` identifier carries a suffix. Several test networks exist, so
a `testnet` identifier without a suffix is ambiguous. The identifiers
`mainnet`, `devnet`, and `simnet` each name one network. These identifiers
MUST NOT carry a suffix.

Producers MUST emit identifiers in this canonical form. Consumers MUST compare
identifiers by exact string equality. Consumers MUST NOT normalize case or
separators.

| Identifier   | Network                | Address prefix |
| ------------ | ---------------------- | -------------- |
| `mainnet`    | Kaspa mainnet          | `kaspa`        |
| `testnet-10` | Public test network 10 | `kaspatest`    |
| `devnet`     | Developer network      | `kaspadev`     |
| `simnet`     | Simulation network     | `kaspasim`     |

The table lists the identifiers that were in use when this document was
written. Other suffixed test networks use the same grammar and the `kaspatest`
prefix. Wallets decide which networks they support.

No CAIP-2 namespace for Kaspa was registered when this document was written.
Pull request 193 to the ChainAgnostic namespaces registry proposes one. The
pull request was opened in July 2026 and is not yet merged. It defines the
`kaspa` namespace with exactly the network identifiers of this section as
chain references. Therefore `kaspa:testnet-10` names the same network as the
provider value `testnet-10`.

The proposal encodes a CAIP-10 account as `kaspa:<reference>:<payload>`. The
payload is the address of [Section 7.3](#73-addresses) without its prefix.
The proposal admits only `mainnet` and `testnet-10` as conformant references.
It excludes `devnet` and `simnet` because they do not name globally unique
networks. If a namespace is registered, its chain references SHOULD remain
the network identifiers defined here.

Registration is not a precondition for the use of a network. The grammar above
admits any `testnet` suffix. Therefore a wallet and an app MAY use `testnet-40`
on this interface whether or not a CAIP reference exists for it. Nothing in
this document depends on the registry. An unregistered network affects only
software that addresses networks in CAIP form. That software has no identifier
to name the network.

### 3. Provider Discovery

Wallets and apps discover each other through two events on `window`.

#### 3.1 Events

```typescript
interface KaspaAnnounceProviderEvent extends CustomEvent {
  type: "kaspa:announceProvider";
  detail: KaspaProviderDetail;
}

interface KaspaRequestProviderEvent extends Event {
  type: "kaspa:requestProvider";
}
```

A wallet dispatches `kaspa:announceProvider`. The event carries a
`KaspaProviderDetail`. An app dispatches `kaspa:requestProvider`. The event
carries no payload.

#### 3.2 Provider info

```typescript
interface KaspaProviderInfo {
  readonly uuid: string;
  readonly name: string;
  readonly icon: string;
  readonly rdns: string;
}
```

- `uuid` MUST be a version 4 UUID as defined in RFC 9562, in the canonical
  lowercase hyphenated form. It identifies one provider instance for the
  lifetime of the page. The wallet MUST generate a new `uuid` on every page
  load.
- `name` is a human-readable name of the wallet, for display.
- `icon` MUST be a `data:` URI as defined in RFC 2397 that decodes to an
  image. The image SHOULD be square with a minimum resolution of 96 by 96
  pixels. PNG, WebP, and SVG are RECOMMENDED formats.
- `rdns` MUST be a reverse domain name identifier, such as
  `com.example.wallet`. A reverse domain name identifier is a valid domain name
  under RFC 1034 with its labels in reverse order. Reverse domain naming is
  only a naming convention. The identifier asserts nothing about domain
  ownership and carries no authenticity (see
  [Security Considerations](#security-considerations)). `rdns` MUST be stable
  across page loads and across versions of the same wallet. This stability lets
  an app recognize a wallet that it has seen before.

Apps SHOULD NOT use `rdns` or `name` for feature detection. An app discovers
capabilities when it calls methods, as described in
[Section 4.1](#41-request).

A wallet MAY include additional properties in `KaspaProviderInfo`. Apps MUST
ignore properties that they do not recognize.

#### 3.3 Provider detail

```typescript
interface KaspaProviderDetail {
  readonly info: KaspaProviderInfo;
  readonly provider: KaspaProvider;
}
```

`provider` is the object defined in [Section 4](#4-provider-interface).

#### 3.4 Wallet requirements

A provider is **ready** when the object described in
[Section 4](#4-provider-interface) exists and can accept `request` calls.
When its provider is ready, a wallet MUST do these steps in this order:

1. add an event listener for `kaspa:requestProvider` on `window`
2. dispatch a `kaspa:announceProvider` event.

The announcement on load reaches apps that sent a request before the wallet
finished injection. The answer to a request reaches apps that initialized
after the wallet.

Every `kaspa:announceProvider` event that one provider instance dispatches MUST
carry the same `uuid` and the same `provider` object. The wallet SHOULD freeze
`detail` and `detail.info` with `Object.freeze()` before it dispatches the
event. A frozen announcement prevents page scripts from altering the
announcement during dispatch. A frozen announcement does not authenticate the
announcer. See [Security Considerations](#security-considerations).

A wallet MUST NOT remove its `kaspa:requestProvider` listener for the lifetime
of the page.

#### 3.5 App requirements

An app MUST add an event listener for `kaspa:announceProvider` on `window`
before it dispatches `kaspa:requestProvider`. An app MUST NOT remove that
listener for the lifetime of the page. A listener that stays in place lets the
app discover wallets that are injected later.

An app SHOULD deduplicate announcements by `uuid`, which identifies one
provider instance. An app MAY also group providers by `rdns` to recognize a
wallet that it used before. The `rdns` value is stable across page loads.

Two announcements that carry the same `uuid` claim to come from the same
instance. If they differ in `name`, `icon`, `rdns`, or the `provider` object,
the app SHOULD treat the later one as suspicious. If they differ in this way,
the app SHOULD NOT silently replace the earlier one. A difference only in
properties that this document does not define is not by itself a reason for
suspicion. The same rules apply to two announcements that share an `rdns` but
carry different `uuid` values.

An app MAY dispatch `kaspa:requestProvider` again at any time to refresh its
list of providers.

#### 3.6 Icons

An SVG image can contain script. Apps and libraries MUST render icons only
through an `<img>` element or an equivalent mechanism that does not execute
script. Apps and libraries MUST reject an `icon` value that is not a `data:`
URI.

#### 3.7 No shared global

This document does not define a global variable such as `window.kaspa`. A
wallet MAY expose a vendor-specific global for its own purposes. An app
MUST NOT require such a global. A wallet MUST NOT rely on such a global for
discovery.

### 4. Provider Interface

`KaspaRpcSchema` names one entry per method of [Section 6](#6-rpc-methods).
Each entry gives the parameter tuple and the result type of that method.
`KaspaProviderEvents` names one entry per event of
[Section 4.4](#44-events). The file
[kcc-0012/interfaces.ts](kcc-0012/interfaces.ts) contains both types.

```typescript
type KaspaRpcMethod = keyof KaspaRpcSchema;

type RequestArguments<M extends KaspaRpcMethod = KaspaRpcMethod> =
  KaspaRpcSchema[M]["params"] extends readonly []
    ? { readonly method: M; readonly params?: KaspaRpcSchema[M]["params"] }
    : { readonly method: M; readonly params: KaspaRpcSchema[M]["params"] };

interface KaspaProvider {
  request<M extends KaspaRpcMethod>(
    args: RequestArguments<M>,
  ): Promise<KaspaRpcSchema[M]["result"]>;
  on<E extends keyof KaspaProviderEvents>(
    event: E,
    listener: KaspaProviderEvents[E],
  ): this;
  removeListener<E extends keyof KaspaProviderEvents>(
    event: E,
    listener: KaspaProviderEvents[E],
  ): this;
}
```

A wallet that serves vendor methods or emits vendor events adds its own
entries to `KaspaRpcSchema` and `KaspaProviderEvents`. The wallet does not
weaken these signatures.

#### 4.1 request

`request` submits one RPC call. The provider MUST identify the RPC method by
`method`. The provider MUST accept the parameters of the method as `params`.
Every method in this document takes `params` as an array. The definition of the
method gives the elements of that array.

A method that takes no parameters accepts `params` as `undefined` or as an
empty array. An omitted `params` member and a `params` member set to
`undefined` are both accepted as `undefined`.

The returned Promise MUST either resolve with the result of the RPC method or
reject with a `ProviderRpcError` ([Section 4.3](#43-errors)). The Promise
MUST NOT resolve with a transport envelope such as a JSON-RPC response
object.

The Promise MUST reject when:

- the provider does not support the method, with code `4200`;
- the method is restricted and the origin is not authorized, with code
  `4100`;
- `params` does not match the method's definition, with code `-32602`;
- the user declines a request that needs consent, with code `4001`;
- the method requires the wallet's remote and the provider is disconnected,
  with code `4900`; or
- the provider encounters any other failure, with code `-32603` unless a
  more specific code of [Section 8](#8-error-codes) applies.

These codes are the EIP-1193 and EIP-1474 values. This document keeps them
unchanged so that error-handling code for an Ethereum wallet also works here.
[Section 8](#8-error-codes) lists every assigned code and reserves the rest.

An app can rely only on the methods that [Section 6](#6-rpc-methods) marks
Required. An app detects any other method, standard or vendor, when it calls
the method and handles code `4200`. A provider MUST reject an unsupported
method with `4200` before any user interaction and before `params`
validation.

A provider MAY support methods beyond those that this document defines. The
provider MUST name such a method with a vendor prefix that cannot collide
with future assignments in [Section 6](#6-rpc-methods). The prefix is the
reverse domain name of the wallet, followed by an underscore, for example
`com.example.wallet_customMethod`. Vendor methods follow the same
authorization rules as restricted methods.

#### 4.2 Connectivity

The provider is **connected** when it can service RPC requests for at least
one network. The provider is **disconnected** when it cannot service RPC
requests for any network.

The provider does not expose connectivity as a value that an app can read. An
app observes connectivity through the `connect` and `disconnect` events of
[Section 4.4](#44-events). An app also observes it through code `4900` from a
method that needs the remote. Connectivity affects only the methods that
[Section 6](#6-rpc-methods) lists as methods that need the remote. The wallet
itself serves the other methods, and the other methods MUST work while the
provider is disconnected.

#### 4.3 Errors

```typescript
interface ProviderRpcError extends Error {
  message: string;
  code: number;
  data?: ProviderErrorData;
}

interface ProviderErrorData {
  readonly submitted?: readonly TransactionId[];
  readonly pskb?: Pskb;
  readonly reason?: RejectionReason;
  readonly [key: string]: unknown;
}
```

- `message` MUST be a human-readable string. The provider MUST reject with
  an object that satisfies `ProviderRpcError`, whatever its implementation
  raises internally. A WebAssembly module or a transport can throw a value
  that is not an `Error`. The provider MUST wrap such a value so that
  `message` and `code` are present.
- When a listed code applies, `code` MUST be an integer from
  [Section 8](#8-error-codes).
- `data` MAY carry any additional information about the error, such as the
  error message of the remote. This document assigns three of its members.
  [Section 6.5](#65-kaspa_sendtransaction) and
  [Section 6.10](#610-kaspa_sendrawpskb) require `submitted`.
  [Section 6.11](#611-kaspa_sendpskb) requires `pskb`, and
  [Section 8](#8-error-codes) defines `reason`. The type stays open so that a
  wallet can add members of its own. A consumer MUST ignore members that it
  does not recognize.

#### 4.4 Events

The provider MUST implement `on` and `removeListener` with the semantics of
the Node.js `EventEmitter` API. `on` registers a listener for an event name.
`removeListener` removes a listener that `on` registered earlier. Both
methods return the provider.

The provider MUST emit the following events under the stated conditions.

##### connect

When the provider becomes connected, both on first initialization and after a
`disconnect` event, the provider MUST emit `connect` with:

```typescript
interface ProviderConnectInfo {
  readonly networkId: NetworkId;
}
```

`networkId` is the network identifier of the current network.

##### disconnect

When the provider becomes disconnected, the provider MUST emit `disconnect`
with a `ProviderRpcError`. The `code` of the error MUST be a `CloseEvent`
status code that the WebSocket API defines (RFC 6455, Section 7.4). For a
temporary loss of the connection to the remote, the code `1013` is
RECOMMENDED. This code space comes from EIP-1193 and is distinct from the
registry of [Section 8](#8-error-codes).

##### networkChanged

When the current network changes, the provider MUST emit `networkChanged`
with the new network identifier.

##### accountsChanged

When the value that `kaspa_accounts` would return changes, the provider MUST
emit `accountsChanged` with the new value. The new value is an array of
address strings. Cases that change the value include:

- a grant or a revocation of authorization;
- a change of the active disclosed address, or of the set of disclosed
  addresses;
- a lock or an unlock of the wallet; and
- a network change that re-encodes the addresses with a different prefix.

A change in the funds of an account does not by itself change the value
`kaspa_accounts` would return. The provider MUST NOT emit `accountsChanged`
for that reason alone. This document defines no balance event.
[Section 6.14](#614-kaspa_getbalance) says how an app reads a later figure.

##### message

The provider MAY emit `message` to deliver a notification that the events
above do not cover, with:

```typescript
interface ProviderMessage {
  readonly type: string;
  readonly data: unknown;
}
```

This document assigns no `type` values. This document reserves values that
begin with `kaspa_` for future KCCs. A wallet MAY emit vendor types that
start with its reverse domain name and an underscore. An app MUST ignore
types that it does not recognize.

### 5. Authorization

#### 5.1 Origin scope

The wallet grants authorization to an origin. The wallet MUST track
authorization per origin. The wallet MUST NOT let one origin observe or reuse
the authorization of another origin. An app is authorized if, and only if, its
origin holds the `kaspa_accounts` permission of
[Section 6.13](#613-permissions).

Before an origin is authorized:

- the provider MUST resolve `kaspa_accounts` with an empty array, and the
  wallet MUST NOT prompt;
- the provider MUST reject every restricted method with code `4100` without
  user interaction; and
- the provider services unrestricted methods as defined.

#### 5.2 Unrestricted methods

The following methods are unrestricted: `kaspa_requestAccounts`,
`kaspa_accounts`, `kaspa_networkId`, `wallet_switchNetwork`,
`wallet_requestPermissions`, `wallet_getPermissions`, and
`wallet_revokePermissions`. Every other method defined in this document is
restricted.

#### 5.3 Consent

If a method's definition says that it prompts the user, the provider MUST NOT
complete it without explicit user confirmation in an interface that the wallet
controls and that the page cannot alter. The wallet MUST identify the
requesting origin in the confirmation. If the user declines, the provider MUST
reject with code `4001`.

A wallet MAY let the user set a standing policy in that same interface. A
standing policy confirms requests from an origin without a prompt when the
requests stay within limits that the user chose. An example of a limit is a cap
per transaction or per period. A request that the policy admits counts as
confirmed. If the policy does not admit a request, the request MUST receive the
user's confirmation as above. The wallet MUST NOT let the page create, read, or
alter a policy.

If the wallet refuses a request under a limit, the provider rejects it with
code `-32005`. The limit can be the wallet's own limit or a limit of the
policy.

#### 5.4 Watch-only accounts

A wallet MAY authorize a watch-only account
([Section 1](#1-definitions)). The wallet can derive the addresses of that
account and cannot produce a signature for them. When a method needs a
signature from such an account, the provider MUST reject with code `4100`.
The provider SHOULD say in the error's `message` that the account cannot
sign. A wallet SHOULD make the distinction visible when the user authorizes
the account. Nothing in an address reveals that the account is watch-only.

#### 5.5 Locked wallets

While the wallet is locked, the provider MUST resolve `kaspa_accounts` with an
empty array. When the wallet locks, the provider MUST emit `accountsChanged`
with an empty array. For `kaspa_requestAccounts`, the wallet SHOULD prompt the
user to unlock. For a restricted method, the wallet MAY prompt the user to
unlock, or the provider MAY reject with code `4100`.

#### 5.6 Pending requests

A request that prompts the user can be pending for an origin. While one is
pending, the provider MAY reject another request of the same method from
that origin with code `-32002`.

### 6. RPC Methods

This section is a registry of method names. Names that begin with `kaspa_`
and `wallet_` are reserved for this KCC and for future KCCs. Unassigned names
are reserved. An implementation MUST NOT give a local meaning to an unassigned
name.

| Method                      | Required | Restricted | Prompts | Ethereum analogue           |
| --------------------------- | -------- | ---------- | ------- | --------------------------- |
| `kaspa_requestAccounts`     | Yes      | No         | Yes     | `eth_requestAccounts`       |
| `kaspa_accounts`            | Yes      | No         | No      | `eth_accounts`              |
| `kaspa_networkId`           | Yes      | No         | No      | `eth_chainId`               |
| `kaspa_getBalance`          | No       | Yes        | No      | none                        |
| `kaspa_getNotes`            | No       | Yes        | Yes     | none                        |
| `kaspa_requestReceiveAddress` | No     | Yes        | No      | none                        |
| `kaspa_signMessage`         | No       | Yes        | Yes     | `personal_sign`             |
| `kaspa_sendTransaction`     | No       | Yes        | Yes     | `eth_sendTransaction`       |
| `kaspa_signTransaction`     | No       | Yes        | Yes     | `eth_signTransaction`       |
| `kaspa_signInputs`          | No       | Yes        | Yes     | none                        |
| `kaspa_sendRawTransaction`  | No       | Yes        | No      | `eth_sendRawTransaction`    |
| `kaspa_signPskb`            | No       | Yes        | Yes     | none                        |
| `kaspa_sendRawPskb`         | No       | Yes        | No      | `eth_sendRawTransaction`    |
| `kaspa_sendPskb`            | No       | Yes        | Yes     | `eth_sendTransaction`       |
| `wallet_switchNetwork`      | No       | No         | Yes     | `wallet_switchEthereumChain`|

| `wallet_revokePermissions`  | Yes      | No         | No      | `wallet_revokePermissions`  |

A conforming provider MUST implement every method that is marked Required. A
conforming provider MAY implement the other methods. A method that is marked
Prompts requires consent as defined in [Section 5.3](#53-consent), except
where that method's section says an existing grant skips the prompt. The
Ethereum analogue column is informative.

Four methods submit a transaction to the wallet's remote, and so they require
the remote:

- `kaspa_sendTransaction`
- `kaspa_sendRawTransaction`
- `kaspa_sendRawPskb`
- `kaspa_sendPskb`

Only these four methods MAY reject with code `4900` while the provider is
disconnected. The wallet alone serves every other method in this document.
This includes account enumeration, balance and note reporting, receive
addresses, network reporting, message signing, transaction signing, and
bundle signing. Every other method MUST work while the provider is
disconnected.

[Section 7](#7-encodings) defines the types that this section names
(`Address`, `Hex`, `Uint64`, `Amount`, `NetworkId`, `TransactionId`,
`SerializedTransaction`, `Pskb`).

#### 6.1 kaspa_requestAccounts

```text
params: []
result: Address[]
```

This method requests access to the user's accounts. If the origin is not
authorized, the wallet MUST prompt the user to authorize it. In that prompt,
the wallet MAY let the user choose which accounts to authorize and which
addresses of those accounts to disclose. If the origin is already authorized
and the wallet is unlocked, the provider MUST resolve without a prompt.

On success, the result MUST be a non-empty array of disclosed addresses, the
active disclosed address first, each encoded for the current network. After
success, `kaspa_accounts` MUST return the same value until it changes.

The array lists disclosed addresses. It MAY hold several. They MAY belong to
more than one authorized account. This document does not constrain which
accounts a wallet offers or which of them the user authorizes. The wallet
MUST NOT include an address of an account the user did not authorize. An app
MAY use any disclosed address, and no change of the wallet's selection is
necessary.

The first element is the active disclosed address
([Section 1](#1-definitions)). When an app needs one address and has no
other preference, the app SHOULD default to the first element.

A wallet whose account contains one address returns that address. For that
wallet the disclosed address is the whole account, and a rule that names the
account names that address.

The result MAY include an address of a watch-only account. From the address
alone, an app cannot tell whether the wallet can sign for that account.

#### 6.2 kaspa_accounts

```text
params: []
result: Address[]
```

This method returns the disclosed addresses of the accounts that are
authorized for the origin, under the rules of
[Section 6.1](#61-kaspa_requestaccounts): the active disclosed address is
first, and each address is encoded for the current network. If the origin is
not authorized or the wallet is locked, the method returns an empty array.
The wallet MUST NOT prompt. The result is the disclosed addresses only. It
is not the balance of an account, and it is not the list of every address in
an account.

#### 6.3 kaspa_networkId

```text
params: []
result: NetworkId
```

This method returns the network identifier of the current network. The wallet
MUST NOT prompt.

#### 6.4 kaspa_signMessage

```text
params: [message: string, address: Address]
result: Hex
```

This method signs `message` with the private key of `address` according to
KIP-5. The wallet hashes the UTF-8 encoding of `message` with BLAKE2b-256,
keyed with `PersonalMessageSigningHash`. The wallet then signs the digest with
a BIP-340 Schnorr signature. The result is the 64-byte signature as 128
hexadecimal characters.

`address` MUST be a disclosed address of an account that is authorized for
the origin. If it is not, the provider MUST reject with code `4100` and MUST
NOT prompt. The provider MUST NOT use the error to distinguish an undisclosed
address of an authorized account from an address that belongs to no
authorized account. `address` MUST be a version 0 or a version 1 address as
defined in [Section 7.3](#73-addresses). If it is not, the provider MUST
reject with code `-32602`.

Before it signs, the wallet MUST display the complete `message` and the
signing address to the user. The wallet MAY use auxiliary randomness when it
signs. Verifiers MUST NOT assume a deterministic signature.

A verifier obtains the public key from the address payload. The 32-byte
payload of a version 0 address is the x-only public key. For a version 1
address, the verifier removes the first byte of the 33-byte payload, and the
remainder is the x-only public key. A version 1 address selects an ECDSA key.
The signature is still a Schnorr signature over the x-only form of that key,
because KIP-5 defines one scheme. The address version selects the key, not
the scheme.

#### 6.5 kaspa_sendTransaction

```text
params: [{
  from?: Address,
  outputs: Array<{ address: Address, amount: Amount }>,
  payload?: Hex,
  priorityFee?: Amount
}]
result: TransactionId
```

This method asks the wallet to build, sign, and submit a transaction. The
transaction pays `amount` sompi to each output `address`. The wallet selects
inputs, adds a change output when one is needed, sets the fee, signs, and
submits.

When `from` is absent, the wallet selects inputs from the selectable set of
the account that contains the active disclosed address, across every address
of that account. When `from` is present, `from` names one address and the
wallet selects inputs only among outputs at that address. `from` MUST be an
address of an authorized account ([Section 1](#1-definitions)). The address
does not have to be a disclosed address. Otherwise, the provider MUST
reject with code `4100`. An address of an account the user did not authorize
is the same code. For an account that contains one address, the absent and present
cases select the same outputs. An app that passes `from` spends only that
address, including when the account holds other outputs. An app that wants
the account omits `from`.

The selectable set is the balance set of that account
([Section 6.14](#614-kaspa_getbalance)), minus every output spent by an
outstanding submission of this wallet, minus every output that carries a
covenant id. An outstanding submission is a transaction this wallet has
submitted to its remote for the current network, that the wallet's view does
not accept, and that the wallet has not dropped. The wallet drops a
submission when it abandons the transaction before acceptance, or when it
observes a rejection after which the remote will not accept the transaction.
A dropped submission no longer removes its outputs.

`kas` still includes an output that an outstanding submission spends, and it
includes sompi on a covenant output the account can move. This method selects
neither. `kas` can therefore be larger than the amount this method can pay.
If the selectable outputs cannot pay the requested outputs and the fee, the
provider MUST reject with code `-32000` before it submits anything. That
error has no `submitted` member.

The wallet MUST select only outputs in the selectable set, and only from the
account named above. It MUST NOT select an output of any other account. The
method gives the app no other control over inputs. An app that must leave a
particular output unspent, or that must spend a covenant output, builds the
transaction itself and uses
[`kaspa_signTransaction`](#66-kaspa_signtransaction) or
[`kaspa_signInputs`](#67-kaspa_signinputs).

- `outputs` MUST be non-empty.
- Every address MUST carry the prefix of the current network. Otherwise, the
  provider MUST reject with code `-32602`.
- When `payload` is present, the wallet places it in the payload field of the
  transaction.
- When `priorityFee` is present, the wallet adds it to the minimum fee that it
  would otherwise pay.
- When there is change, the wallet MUST pay it to the same account the
  inputs came from. The wallet MAY pay an address the inputs came from, or a
  fresh address of that account.
- A provider implements [`kaspa_getBalance`](#614-kaspa_getbalance) when a
  call to that method would not be rejected with code `4200`. Implementation
  is a property of the provider. It does not depend on the origin. Code
  `4100` means the caller is not authorized or the wallet is locked. It does
  not mean the method is unimplemented.
- If the provider does not implement `kaspa_getBalance`, a fresh change
  address becomes part of the value that `kaspa_accounts` returns, and the
  provider MUST emit `accountsChanged`. An app that sums disclosed addresses
  then still sees the change.
- If the provider implements `kaspa_getBalance`, a fresh change address MUST
  NOT be added to `kaspa_accounts` only because it received change, and
  `accountsChanged` MUST NOT be emitted only for that reason. The new output
  is part of `kas` once the transaction that creates it is accepted
  ([Section 6.14](#614-kaspa_getbalance)). Until that transaction is
  accepted, the new output is not in the balance set, and the outputs the
  transaction spends remain in the balance set.

The wallet MUST display these items in full before it prompts the user:

- every output address and amount,
- the fee,
- the payload, when present.

When every selected input is a disclosed address, that list is the whole of
this display requirement. When any selected input is not a disclosed address,
the wallet MUST also show the user the address or the script of each selected
input, and the amount of that input. The result of the method is still only
the transaction id. The wallet MUST NOT add such an address to
`kaspa_accounts` because the user was shown it.

If the remote rejects the transaction, the provider MUST reject with code
`-32003`. In that case, the provider SHOULD place the remote's message in
`data`.

The provider MUST return codes `4001`, `4100`, `-32602`, and `-32000` only
before the wallet submits anything. Code `-32003` means that the remote
accepted nothing. The wallet can submit the transaction and then not learn the
outcome, for example because the connection to the remote was lost. In that
case, the wallet MUST reject with code `4900` if it is now disconnected, and
with code `-32603` otherwise.

The wallet MUST also place the transaction's identifier in the `data` member of
the error as `submitted`. `submitted` is an array of one `TransactionId`. The
app can then look the transaction up before it pays again. An error without
`submitted` means that the wallet submitted nothing.

#### 6.6 kaspa_signTransaction

```text
params: [{
  transaction: SerializedTransaction,
  signInputs: Array<{
    index: number,
    sighashType?: number,
    signatureType?: "schnorr" | "ecdsa",
    redeemScript?: Hex
  }>
}]
result: SerializedTransaction
```

This method signs the listed inputs of a transaction that the app built. It
returns the transaction with the signature scripts of those inputs filled in.
The wallet MUST NOT submit the transaction.

- `signInputs` MUST be non-empty. Every `index` MUST be a valid input index.
  If either condition fails, the provider MUST reject with code `-32602`.
- The wallet MUST sign only the inputs that `signInputs` lists. The wallet
  MUST leave the `signatureScript` of every other input byte-for-byte
  unchanged. An input that a covenant authorizes carries its authorization in
  its signature script. If the wallet overwrites that script, the transaction
  becomes invalid.
- For each listed input, the referenced `utxo.scriptPublicKey` MUST be
  spendable by an authorized account, as
  [Section 7.7](#77-signature-scripts) defines. The address of the key need
  not be a disclosed address. If the input is not spendable by an authorized
  account, the provider MUST reject with code `4100`. The error MUST NOT
  carry an address, a path, or an extended public key. If the wallet cannot
  construct a signature script for the script type, the wallet MUST reject
  with code `-32000`.
- `sighashType` defaults to `1`. The wallet MUST use the requested type. The
  wallet MUST reject a type that it does not implement with code `-32602`,
  rather than substitute another type.
- `signatureType` defaults to the type that the script public key implies
  ([Section 7.7](#77-signature-scripts)). The wallet MUST reject a combination
  that it does not implement with code `-32602`.
- The wallet MUST compute the signature hash as the consensus rules for the
  transaction's `version` define it, over the transaction exactly as received,
  including `payload`, `lockTime`, `subnetworkId`, `gas`, and the covenant
  binding of every output. For `version` 0, the hash also covers the sig-op
  count of every input. For `version` 1 or greater, the hash covers neither the
  sig-op count nor the compute budget of any input. A compute budget is
  therefore not protected by a signature. The returned transaction MUST equal
  the received one except for the `signatureScript` of each listed input and
  the `id` field. The `id` field MUST equal the identifier of the returned
  transaction.
- The wallet MUST display these items in full before it prompts the user:
  - every output amount and address or script,
  - the fee: the sum of the listed and unlisted input amounts minus the sum
    of the output amounts,
  - the net change in the balance of each account that signs. The figure is
    the outputs that pay any address of the account, minus the inputs that
    the account signs. One account is one figure, including when several of
    its addresses sign,
  - the payload, when present.

  In a transaction that the user shares with other parties, the fee alone can
  hide that the user commits a large input.

The returned transaction contains the inputs the app supplied. The wallet
MUST NOT add an address to `kaspa_accounts`, and MUST NOT emit
`accountsChanged`, only because it signed an input at that address.

#### 6.7 kaspa_signInputs

```text
params: [{
  transaction: SerializedTransaction,
  signInputs: Array<{
    index: number,
    address: Address,
    sighashType?: number,
    signatureType?: "schnorr" | "ecdsa"
  }>
}]
result: Hex[]
```

This method signs the signature hash of each listed input of a transaction
that the app built. The wallet signs each hash with the private key of
`address` and returns the signatures. The app constructs the signature
scripts itself. The wallet MUST NOT modify or submit the transaction.

The result holds, at each position, the signature for the input that is
listed at that position. For `schnorr`, the signature is the 64-byte BIP-340
signature. For `ecdsa`, the signature is the 64-byte compact encoding of an
ECDSA signature. Each signature is 128 hexadecimal characters, without the
sighash type byte.

The method serves inputs whose signature script the wallet cannot construct,
because the signature is one argument among others. One example is a covenant
input whose script carries the owner's transaction signature, as the
key-based owner schemes of [KCC-20](kcc-0020.md) do. Another example is a
script that the wallet does not recognize.

- `signInputs` MUST be non-empty. Every `index` MUST be a valid input index.
  If either condition fails, the provider MUST reject with code `-32602`.
- `address` MUST be an address of an authorized account. It need not be a
  disclosed address. Otherwise, the provider MUST reject with code `4100`
  and MUST NOT prompt. The error MUST NOT carry an address, a path, or an
  extended public key. The script of the input can omit `address`. The app
  places the signature where the script expects it.
- `sighashType` defaults to `1`. `signatureType` defaults to the type of the
  address version (`schnorr` for version 0, `ecdsa` for version 1). The rules
  of [Section 6.6](#66-kaspa_signtransaction) for unimplemented values apply.
- The wallet computes the signature hash as in Section 6.6, over the
  transaction exactly as received.
- The wallet MUST display these items before it prompts the user:
  - the items that Section 6.6 requires,
  - for each listed input, the amount of the UTXO that the input spends,
  - for each listed input, the account that signs the input.

  The wallet SHOULD warn when `sighashType` is not `1`. Such a signature does
  not commit to the whole transaction.

#### 6.8 kaspa_sendRawTransaction

```text
params: [transaction: SerializedTransaction]
result: TransactionId
```

The wallet submits a fully signed transaction to its remote and returns the
identifier of the transaction. The wallet MUST NOT modify the transaction. The
wallet SHOULD NOT prompt. If the remote rejects the transaction, the provider
MUST reject with code `-32003` and SHOULD place the message of the remote in
`data`.

#### 6.9 kaspa_signPskb

```text
params: [pskb: Pskb]
result: Pskb
```

The wallet signs a bundle of partially signed Kaspa transactions
([Section 7.8](#78-partially-signed-transaction-bundles)) in the Signer
role.

An input is spendable when an authorized account can spend its `utxoEntry`,
as defined in [Section 7.7](#77-signature-scripts). For every spendable
input of every transaction in the bundle, the wallet computes the signature
hash of the transaction that the PSKT object describes. The wallet uses the
`sighashType` of that input. The wallet then adds one entry to the
`partialSigs` of that input. The entry maps the compressed public key of the
signing account to the signature. The wallet MUST NOT add a
`bip32Derivations` entry, an `xpubs` entry, a derivation path, or an extended
public key. Entries the request already carried stay in the bundle.

- The wallet MUST NOT add, remove, or reorder transactions, inputs, or
  outputs. The wallet MUST NOT modify any other member. The wallet MUST NOT
  set `finalScriptSig`. The wallet MUST NOT submit anything. Finalization
  and extraction are the work of the app. The wallet does not change the
  inputs that it cannot spend.
- The wallet MUST reject with code `-32602` a bundle in which any input of
  any transaction lacks a `utxoEntry`. The signature hash commits to the
  spent outputs. The reference implementation aborts on such a transaction.
- The wallet MUST use the `sighashType` of each input. If an input that the
  wallet would sign carries a `sighashType` that the wallet does not implement,
  the wallet MUST reject with code `-32602` rather than substitute another
  type.
- If no input in the bundle is spendable by an authorized account, the
  provider MUST reject with code `4100`. The key need not belong to a
  disclosed address. The error MUST NOT carry an address, a path, or an
  extended public key.
- Before it prompts, the wallet MUST display, in full, the net change in the
  balance of each account that signs, computed as in Section 6.6, and the
  following items for every transaction that it signs:
  - every output amount and address or script
  - the fee
  - the payload, when present

#### 6.10 kaspa_sendRawPskb

```text
params: [pskb: Pskb]
result: TransactionId[]
```

The wallet finalizes, extracts, and submits every transaction of a fully
signed bundle ([Section 7.8](#78-partially-signed-transaction-bundles)).

For each PSKT object, in order, the wallet does the following steps:

1. The wallet sets the `finalScriptSig` of each input to a concatenation of
   segments, one per `partialSigs` entry. The segments follow the order of the
   entries given below. Each segment is a 65-byte data push (`41`). The pushed
   data is the signature in its 64-byte form followed by the `sighashType` byte
   of the input.

   For a `schnorr` entry, the 64-byte form is the BIP-340 bytes. For an `eCDSA`
   entry, the 64-byte form is the compact r and s encoding derived from its DER
   bytes. When `s` exceeds half the curve order, the wallet replaces `s` with
   `n - s`. Consensus verification accepts only the lower value. When
   `redeemScript` is present, one data push of `redeemScript` follows the last
   segment.
2. The wallet extracts the transaction that the PSKT object describes, as
   defined in [Section 6.9](#69-kaspa_signpskb), with those signature
   scripts. The wallet validates the script of every input.
3. The wallet submits the transaction to its remote with orphan transactions
   disallowed. The wallet records the identifier that the remote returns.
   The result lists the identifiers in bundle order.

An input can have more than one entry. The wallet then orders the entries by
the position at which the key of each entry first occurs in `redeemScript`. The
key occurs as a 32-byte x-only push or as a 33-byte compressed push.
`OP_CHECKMULTISIG` consumes public keys in script order and accepts signatures
only in that order.

Such an input MUST have a `redeemScript` in which the key of every entry
occurs. Otherwise, the wallet MUST reject with code `-32000`. The wallet MUST
also reject with code `-32000` an `eCDSA` value that is not a strictly
DER-encoded signature.

- The wallet MUST reject with code `-32602` a PSKT object with no outputs.
- If finalization or validation fails, the wallet MUST reject with code
  `-32000`. If the remote rejects a transaction, the wallet MUST reject with
  code `-32003`.
- The wallet MUST stop at the first failure. The wallet MUST place the
  identifiers of the transactions that it already submitted in the `data`
  member of the error as `submitted`. `submitted` is an array of
  `TransactionId`. The app can then determine the progress of a dependent
  chain.
- Before finalization, the wallet MUST check `global.txVersion` and MUST reject
  with code `-32000` a version that its implementation cannot extract. The
  reference implementation cannot extract `txVersion` 1 or greater. It aborts
  rather than returns an error for such a version.
- An input is standard when its `utxoEntry.scriptPublicKey` is one of the
  types of [Section 7.4](#74-script-public-keys). Before finalization, the
  wallet MUST reject with code `-32000` a PSKT object with a non-standard
  input. Extraction itself accepts any satisfiable script. The reference
  wallet aborts on a non-standard one.
- The wallet SHOULD NOT prompt. A fully signed bundle carries no authority
  that the user has not already granted. The wallet MAY display a summary.

#### 6.11 kaspa_sendPskb

```text
params: [pskb: Pskb]
result: TransactionId[]
```

This method behaves as [`kaspa_signPskb`](#69-kaspa_signpskb) followed by
[`kaspa_sendRawPskb`](#610-kaspa_sendrawpskb) applied to its result. The wallet
obtains a single user confirmation that meets the display requirements of
Section 6.9. Every rule and error of both methods applies. If signing succeeds
but submission fails, the `data` member of the error MUST also carry the signed
bundle as `pskb`, without the PSKT objects that the wallet already submitted
and with the rest in their original order. The app can then resume the chain
with `kaspa_sendRawPskb` without a second signing prompt.

#### 6.12 wallet_switchNetwork

```text
params: [{ networkId: NetworkId }]
result: null
```

This method asks the wallet to make `networkId` the current network. If
`networkId` is already the current network, the provider MUST resolve with
`null` without a prompt. If the wallet does not support the network, the
provider MUST reject with code `4902`. On success, the provider MUST emit
`networkChanged`, and `accountsChanged` if the address encoding changed,
before it resolves. The wallet SHOULD cancel the requests that are pending for
the previous network.

#### 6.13 Permissions

```typescript
interface CaveatTypes {
  restrictReturnedAccounts: Address[];
}

type Caveat = {
  [K in keyof CaveatTypes]: { type: K; value: CaveatTypes[K] };
}[keyof CaveatTypes];

interface Permission {
  invoker: string;
  parentCapability: string;
  caveats: Caveat[];
  date?: number;
}

type PermissionRequest = { [method: string]: object };
```

A `Permission` records that the origin `invoker` is permitted to call the
restricted capability `parentCapability`, subject to `caveats`. `date` is the
time of the grant, in milliseconds since the Unix epoch.

Caveat types form a registry. This document assigns one type. Unassigned
types are reserved.

| Caveat type                | Applies to       | Value                                  |
| -------------------------- | ---------------- | -------------------------------------- |
| `restrictReturnedAccounts` | `kaspa_accounts` | `Address[]`, the disclosed addresses   |

The value of `restrictReturnedAccounts` is the disclosed addresses. It does
not carry a derivation path or an extended public key.

This document does not define a caveat that expresses a spending limit.
[Section 5.3](#53-consent) allows a wallet to enforce a limit of this kind. A
future KCC can define the caveat, so that an app can read the limit with
`wallet_getPermissions`.

This document defines two permissions, `kaspa_accounts` and
`kaspa_getNotes`. An origin that holds `kaspa_accounts` is authorized in the
sense of [Section 5](#5-authorization). `kaspa_getNotes` is the grant to read
the notes of [Section 6.15](#615-kaspa_getnotes). Holding it does not
authorize the origin. A wallet that does not implement `kaspa_getNotes` does
not recognize that permission.

##### wallet_requestPermissions

```text
params: [PermissionRequest]
result: Permission[]
```

The keys of the request object name the permissions that this method requests.
A request that names `kaspa_accounts` MUST behave as `kaspa_requestAccounts`.
A request that names `kaspa_getNotes` requests that permission. The prompt,
when one is required, is the prompt of
[Section 6.15](#615-kaspa_getnotes). If the origin already holds the named
permission, that key does not prompt. If the request names `kaspa_getNotes`
and the origin does not hold `kaspa_accounts`, and the request does not also
name `kaspa_accounts`, the provider MUST reject with code `4100` and MUST
NOT prompt. If the request names both, the provider handles `kaspa_accounts`
first. If the user declines that part, the provider MUST reject with code
`4001` and MUST NOT grant `kaspa_getNotes`. The provider MUST list in the
result every permission that the origin holds after the request. If the
request names a permission that the wallet does not recognize, the provider
MUST reject with code `-32602`.

##### wallet_getPermissions

```text
params: []
result: Permission[]
```

This method returns every permission that the origin holds. For an unauthorized
origin, it returns an empty array. The wallet MUST NOT prompt.

##### wallet_revokePermissions

```text
params: [PermissionRequest]
result: null
```

The keys of the request object name the permissions that this method revokes.
The wallet revokes them without a prompt. After the revocation of
`kaspa_accounts`, the origin is no longer authorized. The provider MUST then
return an empty array from `kaspa_accounts`. The provider MUST also emit
`accountsChanged` with an empty array. Revoking `kaspa_getNotes` removes
that grant only. It does not revoke `kaspa_accounts`, and it does not change
the disclosed addresses. While the origin still holds `kaspa_accounts`, the
next call to `kaspa_getNotes` prompts again
([Section 6.15](#615-kaspa_getnotes)). A request to revoke a permission that
the origin does not hold is not an error.

#### 6.14 kaspa_getBalance

```text
params: []
result: {
  kas: Amount,
  tokens?: Array<{ covenantId: Hex, commitment?: Hex, amount: Amount }>
}
```

This method returns the balance of the account that contains the active
disclosed address ([Section 1](#1-definitions)). It takes no account
argument. Outputs of any other account are excluded, including outputs of an
account that has a disclosed address later in `kaspa_accounts`.

The method is restricted. The permission is `kaspa_accounts`. The wallet
MUST NOT prompt. If `kaspa_accounts` would return an empty array, the
provider MUST reject with code `4100` and MUST NOT prompt, including when
the wallet is locked. That is narrower than
[Section 5.5](#55-locked-wallets), which lets other restricted methods prompt
for an unlock. A wallet that does not implement this method MUST reject it
with code `4200` before any prompt and before it checks parameters.

The method does not need the remote. The provider MUST NOT reject it with
code `4900`. The result is the wallet's view of the current network at the
time of the call. While the provider is disconnected, that view MAY be
stale. The wallet MUST NOT add an output that the view does not contain.

The method does not produce a signature. The provider MUST NOT reject a
watch-only account for being watch-only. Nothing in the result says whether
the account is watch-only.

`kas` is the sum of the sompi amounts of every output in the balance set of
that account. It is an `Amount`
([Section 7.2](#72-unsigned-decimal-strings-and-amounts)). If the sum does
not fit in a `Uint64`, the provider MUST reject with code `-32603` and MUST
NOT truncate or round.

An output is in the balance set when all of the following hold in that view:

- The transaction that created the output is accepted. A transaction is
  accepted when the consensus rules of the current network accept it on the
  selected chain. An output whose creating transaction is not accepted is
  not in the set. An output that exists only in the mempool is not in the
  set.
- No accepted transaction spends the output. An output that an unaccepted
  transaction spends stays in the set. This includes a spend that is only in
  the mempool, and a spend this wallet has submitted and that is not
  accepted.
- The account can move the output with keys of the account alone, as defined
  below. The address of such a key need not be a disclosed address.
- The consensus rules of the current network currently allow the output to
  be spent. A coinbase output that has not matured is not in the set. An
  output that a time lock does not yet allow to be spent is not in the set.

A reorganisation changes the balance set only by changing which transactions
the selected chain accepts. The wallet answers from its current view. It
MUST NOT keep a previous figure after that view has dropped the creating
transaction, and it MUST NOT drop an output that the view still accepts. Two
calls MAY differ. A change of balance alone MUST NOT cause `accountsChanged`.
The provider MUST NOT emit any event solely because the balance changed,
including an event with no payload. An app that needs a later figure calls
this method again.

The account can move an output with its own keys when one of the following
holds. Its own keys are keys of addresses in the account, and no other
party's key is required.

- `scriptPublicKey` is the version 0 or version 1 script of such a key
  ([Section 7.4](#74-script-public-keys)), and that one signature satisfies
  the script.
- `scriptPublicKey` is a version 8 script whose redeem script the wallet
  recognizes, and keys of the account alone satisfy the redeem script.
- The output carries a covenant the wallet can decode, and keys of the
  account alone can produce the owner authorization that spends it. For a
  KCC-20 state, the schemes are the ones KCC-20 Section 3 lists, and the
  match is the one [KCC-2](kcc-0002.md) defines for that scheme:
  - `p2pk-schnorr/v1` counts when `owner` is the public key of a key of the
    account.
  - `p2pkh-schnorr/v1` and `p2pkh-ecdsa/v1` count when `owner` is the hash,
    under that scheme, of a key of the account.
  - `p2sh/v1` counts when the wallet recognizes the redeem script and keys
    of the account alone satisfy it.
  - `covenant-id/v1` counts only when the wallet can produce that covenant's
    authorization from keys of the account alone. If the wallet cannot
    decide, the output is not in the set.

  A state the wallet cannot decode does not match this item. The wallet MUST
  NOT treat an undecoded state as movable. An output that matches a script
  item above is in the set even when this item does not apply.

An output that matches none of these items is not in the set. Sompi on an
output in the set is part of `kas`, including sompi on a covenant output.
The token amount of a covenant output is not sompi and is not part of `kas`.
Membership of the balance set does not by itself select the output in
[`kaspa_sendTransaction`](#65-kaspa_sendtransaction). That method defines
which outputs it spends.

`tokens` reports token totals of the same balance set. The member is
optional.

- When `tokens` is absent, the wallet does not report token totals. An app
  MUST NOT read the absence as zero.
- When `tokens` is present, it is an array, and it MAY be empty. An empty
  array means that every total the wallet reports is zero. It is not a claim
  about a covenant the wallet cannot decode.

Each element is one total:

- `covenantId` is a `Hex` of 64 characters: the covenant id of
  [Section 7.5](#75-serialized-transactions). Producers MUST emit lowercase.
- `commitment` is a `Hex` of 64 characters when the decoded state has an
  extension commitment, and it is omitted otherwise. Producers MUST emit
  lowercase. For a KCC-20 state, `commitment` is `extension_commitment`
  (KCC-20 Section 1) and it is present, including when every byte is zero.
  KCC-20 Section 4 treats different commitments as not fungible, so they are
  different elements.
- `amount` is a `Uint64`. It is the token amount, not sompi. For KCC-20 it
  is the sum of `KCC20State.amount`.

The wallet MUST combine outputs that share a `covenantId` and a `commitment`
into one element. An omitted `commitment` matches only another omitted
`commitment`. The wallet MUST NOT emit an element whose `amount` is `0`. The
wallet MUST order the array by lowercase `covenantId` ascending, then by
`commitment` ascending, and an omitted `commitment` comes before any present
`commitment`. If a token total does not fit in a `Uint64`, the provider MUST
reject with code `-32603` and MUST NOT truncate or round.

Borrowed receive does not by itself remove an output from the set. KCC-20
Section 5 keeps the owner across a borrow. The output counts when the owner
test above still holds.

The result MUST NOT contain an address, an outpoint, a script, a path, an
extended public key, a count of outputs, or any output of another account.

The wallet MAY reject the call with code `-32005`, without prompting, when
the origin exceeds a rate the wallet set. The wallet MUST NOT return a
substitute figure in place of that error.

#### 6.15 kaspa_getNotes

```text
params: []
result: Array<{
  transactionId: TransactionId,
  index: number,
  amount: Amount,
  address?: Address,
  scriptPublicKey: Hex,
  covenantId?: Hex,
  commitment?: Hex,
  tokenAmount?: Uint64,
  state?: Hex,
  redeemScript?: Hex
}>
```

This method returns the notes of the account that contains the active
disclosed address, and of no other account. A note is an output in the
balance set of [Section 6.14](#614-kaspa_getbalance). One element describes
one note.

- `transactionId` is the transaction that created the output.
- `index` is the output index, from 0 to 4294967295.
- `amount` is the sompi amount of the output, as an `Amount`. It is not a
  token amount.
- `address` is present when the wallet associates an address with the
  output, and omitted otherwise.
- `scriptPublicKey` is the script public key of
  [Section 7.4](#74-script-public-keys).
- `covenantId` is present when the output has a covenant id. It is a `Hex`
  of 64 characters. Producers MUST emit lowercase.
- `commitment` is present when the decoded state has an extension
  commitment. It is a `Hex` of 64 characters. Producers MUST emit lowercase.
  For a KCC-20 note the wallet decoded, it is `extension_commitment`.
- `state` is present when the wallet has decoded the covenant state, and
  omitted otherwise. It is that state as `Hex`. For KCC-20 it is
  `EncodeState` of that `KCC20State` ([KCC-1](kcc-0001.md) Section 3.7).
  Producers MUST emit lowercase.
- `tokenAmount` is present when that decoded state is a KCC-20 state, and
  omitted otherwise. It is a `Uint64`. It is the token amount, not sompi:
  `KCC20State.amount`.
- `redeemScript` is present when the output is P2SH, the version 8 script of
  [Section 7.4](#74-script-public-keys), and the wallet can reconstruct the
  redeem script. It is that script as `Hex`. Producers MUST emit lowercase.
  The wallet MUST NOT return a script whose BLAKE2b-256 is not the hash in
  `scriptPublicKey`. Otherwise `redeemScript` is omitted.

The token amount and the state live in the redeem script, which the chain
does not reveal until the output is spent, so an app cannot otherwise select
token notes or build the transaction it then passes to `kaspa_signInputs` or
`kaspa_signTransaction`.

These fields contain public data only. They MAY contain a public key or a
key hash. They MUST NOT contain a private key, an extended key, or a
derivation path.

The wallet MUST order the array by `transactionId` ascending in lowercase
hexadecimal, then by `index` ascending. Taken from the same view as `kas`,
the sum of `amount` over the array equals `kas`. The two methods are
separate calls. Each call uses the view at the time of that call, and two
calls MAY differ.

The result MUST NOT contain a path, an extended public key, a private key,
or a note of an account the user did not authorize. The call does not change
the disclosed addresses. The wallet MUST NOT add an address to
`kaspa_accounts`, and MUST NOT emit `accountsChanged`, because an address
appeared in this result.

The method is restricted. The permission is `kaspa_getNotes`
([Section 6.13](#613-permissions)). The origin MUST also hold
`kaspa_accounts`. If `kaspa_accounts` would return an empty array, the
provider MUST reject with code `4100` and MUST NOT prompt, including when
the wallet is locked. The notes permission is not a substitute for
authorization.

If the origin holds `kaspa_accounts` and does not hold `kaspa_getNotes`, the
provider MUST prompt, as [Section 5.3](#53-consent) defines, including when
the balance set is empty. The prompt MUST tell the user that the origin will
receive every note of the account, including addresses that are not
disclosed, with transaction ids and amounts, and any decoded token amount,
state, and redeem script. If the user approves, the
origin holds `kaspa_getNotes` until
`wallet_revokePermissions` revokes it, and the provider resolves with the
notes. If the user declines, the provider MUST reject with code `4001` and
MUST NOT grant the permission.

If the origin already holds `kaspa_getNotes`, the provider MUST resolve
without a prompt. The grant does not extend to another origin. A later call
MUST NOT prompt while the grant stands.

An empty balance set resolves as an empty array. That array is not an error.
The provider returns it once the permission is held, including on the call
the user has just approved.

A wallet that does not implement the method MUST reject it with code `4200`
before any prompt. The method does not need the remote. The provider MUST
NOT reject it with code `4900`. The wallet MAY reject it with code `-32005`
before prompting, and before returning notes on a later call. It MUST NOT
return a partial list in place of that error.

`wallet_requestPermissions` grants the same permission when its request names
`kaspa_getNotes`, using the prompt text above. That grant does not itself
return notes. The next call to this method does not prompt.

#### 6.16 kaspa_requestReceiveAddress

```text
params: []
result: Address
```

This method returns one address of the account that contains the active
disclosed address. It returns an address the wallet offers for receiving
payment. A wallet that keeps receive addresses apart from change addresses
MUST return a receive address. It MUST NOT return an address of any other
account. An account that contains one address returns that address.

The returned address becomes a disclosed address if it was not already one.
`kaspa_accounts` then returns it. If the array changed, the provider MUST
emit `accountsChanged`. Adding the address MUST NOT by itself change which
element is first. If the address was already disclosed, the array is
unchanged and the provider MUST NOT emit `accountsChanged`.

The method is restricted. The wallet MUST NOT prompt for this method beyond
the authorization the origin already holds. If `kaspa_accounts` would return
an empty array, the provider MUST reject with code `4100` and MUST NOT
prompt, including when the wallet is locked. A wallet that does not
implement the method MUST reject it with code `4200` before any prompt. The
method does not need the remote. The provider MUST NOT reject it with code
`4900`. The result MUST NOT be accompanied by a path or an extended public
key. There is no parameter for an account. The account is the one that
contains the active disclosed address.

### 7. Encodings

#### 7.1 Hexadecimal

`Hex` is a string of an even number of hexadecimal characters with no prefix.
Producers MUST emit lowercase. Consumers SHOULD accept either case.
`TransactionId` is a `Hex` of exactly 64 characters.

#### 7.2 Unsigned decimal strings and amounts

`Uint64` is an unsigned 64-bit integer in the form of a decimal string. The
string has these properties:

- one or more digits
- no sign
- no separators
- no exponent
- no leading zeros, except for the single digit `0`
- a value that is not greater than 18446744073709551615

Every 64-bit quantity on this interface uses this form. An implementation
MUST NOT use a JSON number for a 64-bit quantity. An IEEE 754 double cannot
represent every 64-bit value.

`Amount` is a `Uint64` that counts sompi. One KAS is 100000000 sompi.

#### 7.3 Addresses

`Address` is a Kaspa address string in its standard form. The string is a
prefix from [Section 2](#2-network-identifiers), a colon, and the encoded
payload. Three address versions exist:

| Version | Payload                              | Script type |
| ------- | ------------------------------------ | ----------- |
| 0       | 32-byte x-only Schnorr public key    | P2PK        |
| 1       | 33-byte compressed ECDSA public key  | P2PK ECDSA  |
| 8       | 32-byte BLAKE2b-256 of a redeem script | P2SH      |

Providers MUST return addresses with the prefix of the current network. Apps
MUST NOT strip the prefix.

#### 7.4 Script public keys

In JSON, a script public key is a `Hex`. The first four characters are the
16-bit script version in big-endian byte order. The remainder is the script.
The current script version is 0, so every script public key in this
document begins with `0000`. The scripts for the three address versions are:

| Address version | Script                                      |
| --------------- | ------------------------------------------- |
| 0               | `20` `<32-byte key>` `ac`                   |
| 1               | `21` `<33-byte key>` `ab`                   |
| 8               | `aa` `20` `<32-byte hash>` `87`             |

In these scripts:

- `20` is a data push of 32 bytes
- `21` is a data push of 33 bytes
- `ac` is `OP_CHECKSIG`
- `ab` is `OP_CHECKSIGECDSA`
- `aa` is `OP_BLAKE2B`
- `87` is `OP_EQUAL`

#### 7.5 Serialized transactions

`SerializedTransaction` is the text of a single JSON object (RFC 8259) with
the members below. It is the "safe" JSON schema of the Kaspa WASM SDK. The
SDK produces it with `Transaction.serializeToSafeJSON()` and consumes it with
`Transaction.deserializeFromSafeJSON()`. This section is the normative
definition.

Member names are case-sensitive. A member that is marked optional MAY be
absent or `null`. `Hex[n]` is a `Hex` of exactly `n` characters.

```text
Transaction object
  id               Hex[64]   required  transaction identifier (see below)
  version          integer   required  0 to 65535
  inputs           array     required  Input objects, at least one
  outputs          array     required  Output objects
  subnetworkId     Hex[40]   required
  lockTime         Uint64    required
  gas              Uint64    required
  storageMass      Uint64    optional  also accepted under the name "mass"
  payload          Hex       required  empty string when there is no payload

Input object
  transactionId    Hex[64]   required  identifier of the transaction spent
  index            integer   required  0 to 4294967295, output index spent
  sequence         Uint64    required
  sigOpCount       integer   required  0 to 255
  computeBudget    integer   optional  0 to 65535, defaults to 0
  signatureScript  Hex       required  empty string when unsigned
  utxo             object    required  UtxoEntry object

UtxoEntry object
  address          Address   optional
  amount           Uint64    required  sompi
  scriptPublicKey  Hex       required  Section 7.4
  blockDaaScore    Uint64    required
  isCoinbase       boolean   required
  covenantId       Hex[64]   optional

Output object
  value            Uint64    required  sompi
  scriptPublicKey  Hex       required  Section 7.4
  covenant         object    optional  CovenantBinding object

CovenantBinding object
  authorizingInput integer   required  0 to 65535, index of the input
  covenantId       Hex[64]   required
```

A consumer MUST reject a text in any of the following cases:

- The text is not a JSON object.
- The text lacks a required member.
- A member has a type or form other than the one listed.

A consumer MUST ignore members that are not listed here. A producer SHOULD NOT
emit members that are not listed here. `storageMass` does not enter the
signature hash.

Every input MUST carry a `utxo` entry. The signature hash commits to the
amount and the script public key of the spent output. A consumer MUST NOT
trust the `id` member. A consumer MUST compute the transaction identifier
from the transaction contents. If a producer cannot compute the identifier,
the producer MAY set the `id` member to 64 zero characters.

#### 7.6 Signature hash types

`sighashType` is one of the following values. Any other value is invalid.

| Value | Name                     |
| ----- | ------------------------ |
| `1`   | `SIGHASH_ALL`            |
| `2`   | `SIGHASH_NONE`           |
| `4`   | `SIGHASH_SINGLE`         |
| `129` | `SIGHASH_ALL` with `ANYONECANPAY`    |
| `130` | `SIGHASH_NONE` with `ANYONECANPAY`   |
| `132` | `SIGHASH_SINGLE` with `ANYONECANPAY` |

#### 7.7 Signature scripts

An input is **spendable by an account** when it matches a key of an address
in that account. The address need not be one that `kaspa_accounts` returns.
There are two cases. In the first case, `utxo.scriptPublicKey` is the version
0 or version 1 script of that key. In the second case, the input has a
`redeemScript` and all of the following hold:

- The script public key is the version 8 script whose hash is the
  BLAKE2b-256 of `redeemScript`.
- The wallet recognizes the redeem script.
- That key is a signing key in the redeem script.

The script can need that signature alone or together with the signatures of
other parties. The key decides spendability, not the disclosed list. A key of
an account the user did not authorize does not match. Before it signs, the
wallet MUST derive the script public key from the key it would sign with and
compare it with `utxo.scriptPublicKey`. The comparison is direct or through
the redeem script. The key MAY belong to an address of the authorized account
that `kaspa_accounts` does not list. An account is watch-only
([Section 5.4](#54-watch-only-accounts)) when the wallet cannot produce its
key. This is true whether or not the wallet has recorded the account as
watch-only.

[Section 6.14](#614-kaspa_getbalance) counts an output only when keys of the
account alone can move it. This section also treats an input as spendable
when the account holds one signing key and other parties must sign as well.
`kaspa_sendTransaction` selects from the balance set, with the further
exclusions in [Section 6.5](#65-kaspa_sendtransaction). `kaspa_signPskb` and
`kaspa_signInputs` use this section, so a partial signature is allowed.
`kaspa_signTransaction` uses this section and then requires that the
account's signature alone satisfy the script, as the next paragraphs say.
[Section 6.4](#64-kaspa_signmessage) is not spendability. It still requires a
disclosed address.

Under [Section 6.9](#69-kaspa_signpskb), the wallet adds one partial signature
to every spendable input. Therefore a multi-signature input is spendable by
each of its signers.

Under [Section 6.6](#66-kaspa_signtransaction), the wallet writes the complete
signature script. Therefore, under that method, the redeem script MUST also be
one that the signature of that account alone satisfies. For any other script,
the wallet rejects with code `-32000`. The app then obtains the signature with
[Section 6.7](#67-kaspa_signinputs) and composes the script itself. Before it
returns, a wallet SHOULD verify every signature script that it wrote against
its script public key.

Let `sig` be the 64-byte signature and `t` the one-byte sighash type. The
wallet MUST construct signature scripts as the following table shows, with
the minimal encoding of data pushes. The minimal encoding uses `OP_DATA_1`
through `OP_DATA_75` for pushes of up to 75 bytes, and `OP_PUSHDATA1`,
`OP_PUSHDATA2`, or `OP_PUSHDATA4` for longer pushes.

| Script public key | Default signature type | Signature script                                |
| ----------------- | ---------------------- | ----------------------------------------------- |
| Version 0 P2PK    | `schnorr`              | `41` `sig` `t`                                  |
| Version 1 P2PK    | `ecdsa`                | `41` `sig` `t`                                  |
| Version 8 P2SH    | `schnorr`              | `41` `sig` `t` followed by a push of `redeemScript` |

A Schnorr signature is a BIP-340 signature over the Schnorr signature hash. An
ECDSA signature is the 64-byte compact encoding (r followed by s) of an ECDSA
signature over the ECDSA signature hash. The Kaspa consensus rules define both
hashes for the given sighash type. The two hashes differ from each other. A
wallet MUST use the hash that matches the signature type.

#### 7.8 Partially signed transaction bundles

`Pskb` is the string form of a bundle of partially signed Kaspa
transactions PSKT.

A consumer MUST reject a `Pskb` in any of the following cases:

- The string does not begin with `PSKB`.
- The remainder is not even-length hexadecimal, in lowercase or uppercase.
- The decoded bytes are not the JSON document that this section defines.

The JSON document is an array of **PSKT objects**. The array MAY be empty.
Each PSKT object has exactly these members. A producer MUST emit them in
this order:

```text
PSKT object
  global   object   required  Global object
  inputs   array    required  Input objects
  outputs  array    required  Output objects
```

Every 64-bit quantity in a bundle is a `Uint64Number`. These quantities are
`fallbackLockTime`, `sequence`, `minTime`, `amount`, and `blockDaaScore`. A
`Uint64Number` is an unsigned integer that is not greater than
18446744073709551615. It appears as a JSON number with no fraction, exponent,
or sign.

This departs from [Section 7.2](#72-unsigned-decimal-strings-and-amounts)
because the bundle text is the serialization of the kaspa-wallet-pskt crate.
That crate writes these members as numbers. A `Pskb` MUST round-trip through
that crate byte for byte.

A value above 9007199254740991 (2^53 - 1) is not exact in an IEEE 754 double. A
parser that converts integers to doubles returns a rounded value without an
error. JavaScript's `JSON.parse` is such a parser.

A consumer MUST either decode a bundle with a parser that preserves such
integers exactly, or it MUST reject a bundle that contains one. A parser can
preserve them through the crate itself, a BigInt-aware parser, or the source
text of each number. A wallet MUST NOT re-emit a bundle whose values it
rounded.

Such values do occur. The finalizer of [Section 6.10](#610-kaspa_sendrawpskb)
sets an absent `sequence` to 18446744073709551615. The accept vectors show
this.

```text
Global object
  version           integer   required  PSKT version: 0, 1, or 2; other values invalid
  txVersion         integer   required  0 to 65535, version of the transaction being built
  fallbackLockTime  Uint64Number  optional  omittable or null
  inputsModifiable  boolean   required
  outputsModifiable boolean   required
  inputCount        integer   required  number of inputs
  outputCount       integer   required  number of outputs
  xpubs             object    required  map of extended-public-key string to KeySource; MAY be empty
  id                Hex[64]   optional  omittable or null, transaction identifier
  proprietaries     object    required  map of string to arbitrary JSON; MAY be empty
  payload           Hex       required  hex string or null
```

```text
Input object
  utxoEntry        object    optional  UtxoEntry object; omittable or null
  previousOutpoint object    required  Outpoint object
  sequence         Uint64Number  optional  omittable or null
  minTime          Uint64Number  optional  omittable or null
  partialSigs      object    required  map of compressed-public-key hex to Signature; MAY be empty
  sighashType      integer   required  0 to 255; valid values per Section 7.6
  redeemScript     Hex       required  hex string or null
  sigOpCount       integer   optional  0 to 255; omittable or null
  bip32Derivations object    required  map of public-key hex to KeySource or null; MAY be empty
  finalScriptSig   Hex       required  hex string or null
  proprietaries    object    required  map of string to arbitrary JSON; MAY be empty
```

```text
Output object
  amount           Uint64Number  required  sompi, as a JSON number
  scriptPublicKey  Hex           required  Section 7.4
  redeemScript     Hex           required  hex string or null
  bip32Derivations object        required  map, MAY be empty
  covenant         object        optional  CovenantBinding object; omittable or null
  proprietaries    object        required  map, MAY be empty

UtxoEntry object
  amount           Uint64Number  required  sompi, as a JSON number
  scriptPublicKey  Hex           required  Section 7.4
  blockDaaScore    Uint64Number  required  as a JSON number
  isCoinbase       boolean       required
  covenantId       Hex[64]       optional  omittable or null

Outpoint object
  transactionId    Hex[64]       required
  index            integer       required  0 to 4294967295

CovenantBinding object
  authorizingInput integer       required  0 to 65535
  covenantId       Hex[64]       required

KeySource object
  keyFingerprint   Hex[8]        required
  derivationPath   string        required  BIP-32 path with the leading "m", hardened marked "'", e.g. "m/45'/0'/0/0"
```

##### Signature object

A `Signature` is a JSON object with exactly one member. The member name
selects the scheme. The value is the signature as `Hex`.

| Member    | Scheme         | Value                                 | Length                    |
| --------- | -------------- | ------------------------------------- | ------------------------- |
| `schnorr` | BIP-340        | the 64-byte signature                 | exactly 128 characters    |
| `eCDSA`   | ECDSA, DER     | the DER-encoded signature             | variable, at most 144     |

The member names are exact, including the capitalization of `eCDSA`. That
capitalization is the spelling of the crate. The member `eCDSA` is unrelated to
the `signatureType` value `ecdsa` of [Section 6.6](#66-kaspa_signtransaction).
That value is a parameter of this interface and not a bundle member. A wallet
that acts under [Section 6.9](#69-kaspa_signpskb) produces `schnorr`
signatures.

##### Key and path strings

| Where                                   | Form                                                        |
| --------------------------------------- | ----------------------------------------------------------- |
| keys of `partialSigs`, `bip32Derivations` | compressed public key, 66 hexadecimal characters          |
| keys of `xpubs`                         | Base58Check extended public key with the `xpub` version bytes, on every network |
| `keyFingerprint`                        | `Hex[8]`, the first four bytes of the master key identifier |
| `derivationPath`                        | BIP-32 path beginning with `m`, hardened steps marked with `'` |

A producer MUST emit the keys of public-key maps in the compressed form. A
consumer MAY additionally accept the uncompressed 130-character form.

### 8. Error Codes

Error codes form a registry. This KCC and future KCCs reserve the codes in
the range 4000 to 4999. They also reserve the codes in the range -32768 to
-32000. Unassigned codes in those ranges are reserved. A wallet MAY use codes
outside those ranges for vendor-specific errors.

| Code     | Message                        | Meaning                                                        |
| -------- | ------------------------------ | -------------------------------------------------------------- |
| `4001`   | User Rejected Request          | The user rejected the request.                                 |
| `4100`   | Unauthorized                   | The requested method or account has not been authorized.       |
| `4200`   | Unsupported Method             | The provider does not support the requested method.            |
| `4900`   | Disconnected                   | The provider is disconnected from all networks.                |
| `4901`   | Network Disconnected           | Reserved: no method here targets a network other than the current one. |
| `4902`   | Unrecognized Network           | The wallet does not support the requested network.             |
| `-32700` | Parse error                    | The request could not be parsed.                               |
| `-32600` | Invalid request                | The request is not a valid request object.                     |
| `-32601` | Method not found               | Reserved for pass-through from the remote; providers use `4200`. |
| `-32602` | Invalid params                 | The parameters do not match the method definition.             |
| `-32603` | Internal error                 | An internal error occurred.                                    |
| `-32000` | Invalid input                  | The input is well-formed but cannot be processed.              |
| `-32001` | Resource not found             | A referenced resource does not exist.                          |
| `-32002` | Resource unavailable           | A request of the same kind is already pending.                 |
| `-32003` | Transaction rejected           | The remote rejected the transaction.                           |
| `-32004` | Method not supported           | Reserved for pass-through from the remote; providers use `4200`. |
| `-32005` | Limit exceeded                 | The request exceeds a limit set by the wallet.                 |

When no more specific text is available, the `message` column gives the
RECOMMENDED value of `ProviderRpcError.message`.

When the code is `-32003`, `data.reason` SHOULD name the class of the remote's
rejection with one of the values below. An app can then choose its next step
from this value alone. The values form a registry. Unassigned values are
reserved.

| `reason`           | The remote rejected the transaction because                                  | Usual next step                |
| ------------------ | ---------------------------------------------------------------------------- | ------------------------------ |
| `missing-outpoint` | an input spends an output it does not know or that is already spent          | refresh UTXOs and rebuild      |
| `orphan`           | an input spends an output of a transaction it has not accepted               | submit the parent first        |
| `double-spend`     | another transaction in its mempool spends one of the inputs                  | wait for it or rebuild         |
| `duplicate`        | it already holds or has accepted the transaction                             | treat as submitted             |
| `insufficient-fee` | the fee is below what it accepts                                             | raise `priorityFee`            |
| `mempool-full`     | its mempool is full                                                          | wait and resubmit              |
| `mass`             | the transaction exceeds a compute, storage, or transient mass limit          | split or simplify              |
| `non-standard`     | the transaction is valid but not standard                                    | change the transaction         |
| `invalid`          | the transaction breaks a consensus rule                                      | rebuild                        |

## Rationale

**Why copy Ethereum.** EIP-1193 and EIP-6963 are the most widely deployed
wallet interoperability conventions in any ecosystem. Every developer who has
integrated an EVM wallet knows their shapes. Their failure modes are
documented. Library authors can port existing connector code with a change of
method names. A Kaspa-specific shape would cost adoption and would not buy
anything that the Kaspa model needs, except transaction signing. The
paragraphs below discuss transaction signing.

**Why events rather than a global.** A shared global such as
`window.kaspaProvider` has a problem when several wallets are installed: the
last wallet to write it replaces the others. Its presence at page load also
depends on the injection timing. EIP-6963 solved both problems with an
announce-and-request pair on `window`. This document adopts it unchanged apart
from the event prefix. The KIP-12 draft named the announcement event
`kaspa:provider`. This document uses `kaspa:announceProvider` to mirror
`eip6963:announceProvider` exactly, because the event pair is the one part of
the protocol that every library hard-codes.

**Why `uuid`, `name`, `icon`, and `rdns` are the only standard fields.** These
are the four EIP-6963 fields, and existing wallet-selection user interfaces
know how to render them. The KIP-12 draft also carried an extension `id` and a
`methods` array. The former duplicated `rdns`. The latter advertised
capabilities that a page script could equally announce, so apps could not
trust it. Capability discovery through code `4200` costs one rejected call,
and a page script cannot falsify it.

**Why `kaspa_` and `wallet_` with underscores.** Ethereum separates
chain-scoped methods (`eth_`) from wallet-scoped methods (`wallet_`). JSON-RPC
method names conventionally use an underscore. The KIP-12 draft used
`kaspa:connect` style names. Those names read like event names and collide
with the namespace of the discovery events.

**Why `networkId` rather than `chainId`.** Ethereum's `chainId` is a
hexadecimal integer that identifies a chain. Kaspa's networks are named, not
numbered. Every Kaspa tool already uses the node's own string form, so
`networkId` describes what the field carries. It also matches the vocabulary
of the deployed Kaspa wallets. Those wallets expose a network getter, a
network switch, and a network-changed event. The value is the canonical
identifier of [Section 2](#2-network-identifiers), not a wallet-specific
spelling such as `kaspa_testnet_10`.

**Why an account is one balance.** Some wallets spend one balance from many
addresses: addresses shown to an app, and change addresses that are not.
Treating each address as an account forces the app to be shown every address
before that balance can be known from the addresses it holds. This document
uses "account" for the set the wallet spends together. A wallet that spends
one address is that rule with a set of one address, and `kaspa_accounts`
still returns an array of addresses.
The provider does not return an extended public key or a derivation path.
Either one would let the origin derive addresses the user did not disclose.
This document does not say which path, if any, a wallet uses to derive the
set.

**Why `kaspa_signTransaction` takes a list of inputs.** On an account-based
chain, a wallet signs a whole transaction. In the UTXO model a transaction
routinely mixes inputs owned by the user with inputs owned by other parties.
Some inputs belong to covenants whose signature scripts are already in place.
The app therefore tells the wallet which inputs belong to the wallet, and the
wallet leaves the other inputs unchanged.

**Why `kaspa_signInputs` exists.** `kaspa_signTransaction` writes finished
signature scripts of the layouts in Section 7.7. `kaspa_signPskb` adds partial
signatures to inputs of those same layouts. A covenant can carry the owner's
transaction signature among other script arguments, as the key-based owner
schemes of KCC-20 do. Such a covenant fits neither method. The app can compose
the script but cannot make the signature, and the wallet can make the
signature but cannot compose the script. Without a method that returns the
bare signature, a wallet-held key could not move a token held under such a
scheme through this interface.

The method takes the same transaction and input list as
`kaspa_signTransaction` and names the signing account explicitly. It differs
in its result, so the same display rules apply.

**Why a separate `kaspa_signPskb`.** Multi-party and multi-signature flows
need more than a finished transaction. They need partial signatures from
several signers, redeem scripts, and key-derivation metadata. These accumulate
across participants who do not trust each other. `kaspa_signPskb` carries
those in the bundle format of
[Section 7.8](#78-partially-signed-transaction-bundles).
`kaspa_signTransaction` writes finished signature scripts and suits the
common single-signer case.

An earlier revision omitted the bundle method because only the SDK defined its
schema. Section 7.8 now specifies it. The authors derived the specification
from the kaspa-wallet-pskt crate and verified it against that implementation.

**Why two bundle-submission methods.** An app that has co-signed a bundle
needs a way to submit it to the network. The app would otherwise finalize and
extract the bundle in the page, which requires the SDK in every app that uses
bundles. `kaspa_sendRawPskb` moves that work to the wallet, which already has
the code for it. `kaspa_sendPskb` also signs the bundle, for the
single-signer case. The reference wallet's own broadcast and send operations
do the same, and so did the KIP-12 draft.

The reference implementation skips a transaction that fails and continues with
the next. This document instead requires that the wallet stops at the first
failure and reports what it submitted. A bundle is usually a dependency chain,
and an unreported gap is worse than a reported one.

The reference finalizer also concatenates partial signatures in the order of
their compressed keys. `OP_CHECKMULTISIG` accepts that order only when the
redeem script lists its keys in the same order. Section 6.10 orders them by
the redeem script instead. The conformance vectors carry a case in which the
two orders differ.

**Why `kaspa_getBalance`.** An app that sums disclosed addresses on a public
node misses every undisclosed output of the account, including change. This
method returns one sompi total for the account that contains the active
disclosed address, and token totals when the wallet reports them, without
returning those addresses. It does not prompt. The permission is the one the
origin already holds. `kas` follows acceptance on the selected chain: an
output only in the mempool is excluded, and an accepted output that only an
unaccepted transaction spends is still included. After a reorganisation the
wallet answers from the new view. Amounts are `Uint64` strings. A wallet that
does not implement the method rejects it with `4200`. A wallet that
implements it pays change to the same account and does not disclose a fresh
change address merely because it received change. A wallet that rejects the
method with `4200` still discloses that address, so an app that sums
disclosed addresses does not lose the change.

**Why `from` is one address and its absence is the account.** When `from` is
absent, `kaspa_sendTransaction` selects from the whole account of the active
disclosed address, so a payment can spend change the app has not been shown.
When `from` is present, selection stays on that one address, which is what a
caller that passes the active disclosed address already asked for. An account
of one address makes the two selections the same. Outputs that carry a
covenant id stay out of this method. The app builds those transactions
itself. `kas` can exceed what this method can pay, because `kas` still counts
an output this wallet has submitted and the network has not accepted, and
because `kas` counts sompi on a covenant output.

**Why spendability follows the key.** Section 7.7 already decided spendability
from the key the wallet would sign with, not from the position of an address
in a list. Once an account contains addresses the app has not been shown,
those keys are keys of the authorized account. `kaspa_signTransaction`,
`kaspa_signInputs`, and `kaspa_signPskb` accept them. `kaspa_signMessage`
does not: a message signature would confirm an undisclosed address without
spending an output, and the method rejects that address with `4100` and no
prompt. A script that needs another party's key is spendable here for a
partial signature, and it is not in the balance set, because the account
cannot move it alone.

**Why `kaspa_getNotes` is a permission.** The note list is the cluster:
transaction ids, scripts, and addresses the user had not disclosed. That
requires consent. The consent is one grant per origin, recorded as the
`kaspa_getNotes` permission of [Section 6.13](#613-permissions), and it
lasts until the origin revokes it. A later call does not prompt. The total
does not prompt either, which is why `kaspa_getBalance` and
`kaspa_getNotes` are different methods. A receive address is one address
the user is willing to show. It joins the disclosed list and does not
prompt, because the origin is already authorized. Neither call returns a
path, an extended public key, or a private key. A decoded note may
carry a public key or a key hash in `state` or `redeemScript`. That is
public data. The token amount and the state live in the redeem script,
which the chain does not reveal until the output is spent, so without
these fields an app cannot select the token note or build the transaction
it passes to `kaspa_signInputs` or `kaspa_signTransaction`. A wallet may implement
either method, both, or neither. Code `4200` is the signal.

**Why no node pass-through.** Ethereum providers forward `eth_getBalance` and
similar read methods to the node. An app that holds a disclosed address can
read that address on a public node or an indexer. That read is not the
balance of an account that also holds undisclosed outputs.
`kaspa_getBalance` returns the account total without listing those addresses
and without forwarding the node RPC. A standardized pass-through surface
would tie this document to the node RPC. A future KCC can define one.

**Why no network-adding method.** EIP-3085 exists because a user can add an
EVM chain by URL. The node enumerates Kaspa networks, so `wallet_switchNetwork`
with code `4902` suffices.

**Why sompi strings.** A JavaScript `number` cannot represent every 64-bit
sompi value. A rounding error in an amount is a fund-safety defect. The bundle
format of Section 7.8 is the one exception, which the crate that defines it
imposes. Section 7.8 states the parsing rule that keeps it safe.

**Alternatives considered.** Ethereum is widely regarded as the biggest and
most widely adopted standard, so the authors considered no specific
alternatives. This KCC is a continuation and adaptation of KIP-12.

**Reading guide.** The account rules and the reason for each one are set out
side by side in
[kcc-0012/rationale-hd-account.md](kcc-0012/rationale-hd-account.md). That
file is non-normative. Where it and this document disagree, this document is
authoritative.

## Backwards Compatibility

No previous standard exists. A wallet that spends one address and returns
that address from `kaspa_accounts` still conforms. For that wallet the
account and the disclosed address are the same address. A wallet that
rejects `kaspa_getBalance` with code `4200` still conforms. The method is
optional. For that wallet, a fresh change address is still added to
`kaspa_accounts`. An app that sums disclosed addresses is looking at the
whole account when that code is `4200`, because fresh change is disclosed.
Against a wallet that implements `kaspa_getBalance`, the same sum is only
the disclosed subset, and the app reads the total from the method. An app
that passes the active disclosed address as `from` still spends that address
only. On an account of one address, omitting `from` spends that same
address. A wallet that rejects `kaspa_getNotes` or
`kaspa_requestReceiveAddress` with code `4200` still conforms. Both methods
are optional.

### Partially signed transaction bundles

A canonical `Pskb` ([Section 7.8](#78-partially-signed-transaction-bundles))
is in [kcc-0012/vectors/pskb.json](kcc-0012/vectors/pskb.json), together with
its decoded JSON.

A consumer MUST reject:
- the same string with its `PSKB` prefix removed
- a `PSKB` prefix followed by the hexadecimal of a JSON object rather than an
array
- a `PSKB` prefix followed by odd-length hexadecimal
- a bundle in which an input to be signed carries a `sighashType` of `3`
- a bundle in which an input lacks a `utxoEntry`.

The same file carries vectors for
[`kaspa_sendRawPskb`](#610-kaspa_sendrawpskb). The finalization of these
vectors follows Section 6.10. The extraction uses `kaspa-wallet-pskt` at
workspace version 2.0.1.

The first accept case is a single version 0 P2PK input. Its finalized
`finalScriptSig` is `41`, the 64-byte signature, then `01`. Its submission
resolves with the one identifier
`3e98f2da4347654f164f9a8819a0d2a99a295005db8e8e0ffab2b711b91294ec`.

The second accept case is a 2-of-2 P2SH multisig input that carries both
signatures. Its redeem script lists the key of secret 3 before the key of
secret 2. That order is the reverse of their compressed-key order. When the
bundle is finalized in redeem-script order, it validates and resolves with the
same identifier, because the identifier excludes signature scripts. When the
same bundle is finalized in compressed-key order, it fails validation with the
message `not all signatures empty on failed checkmultisig`.

The wallet MUST reject two cases:

- a PSKT object with no outputs, with code `-32602`
- a 2-of-2 multisig input that carries one signature, with code `-32000`;
  this input finalizes but fails validation

The `extractedTransaction` member of an accept case is informative. It is the
crate's own rendering of the extracted transaction, not a
`SerializedTransaction` of Section 7.5.

### Disclosed addresses

`kaspa_requestAccounts` and `kaspa_accounts` return a JSON array of address
strings ([Section 6.1](#61-kaspa_requestaccounts),
[Section 6.2](#62-kaspa_accounts)). A one-address account is an array of one
address. The array does not carry an extended public key, a derivation path,
or an object in place of an address. The machine-readable cases are in
[kcc-0012/vectors/account.json](kcc-0012/vectors/account.json).

### Account balance

`kaspa_getBalance` returns `kas` as an `Amount` string. `tokens`, when
present, is an array of totals keyed by covenant id and, when the state has
one, extension commitment. Amounts are `Uint64` strings. A JSON number, a
leading zero, an address, or a covenant id that is not 64 hexadecimal
characters is rejected. The balance-set cases and the token-total case are
in [kcc-0012/vectors/balance.json](kcc-0012/vectors/balance.json). For each
balance-set case the file gives the output and whether it is in the set. An
output whose time lock has not expired is out, as is an immature coinbase.
The token case sums two outputs that share a covenant id and a commitment,
keeps a different commitment as a second element, and excludes an output the
account cannot move.

### Change-address disclosure

A fresh change address is added to `kaspa_accounts`, and `accountsChanged`
fires, when the provider does not implement `kaspa_getBalance`. A provider
that implements the method does not add that address only because it received
change, and does not emit `accountsChanged` only for that reason. The cases
are in
[kcc-0012/vectors/change-address.json](kcc-0012/vectors/change-address.json).

### Send input selection

When `from` is absent, `kaspa_sendTransaction` may select any output in the
selectable set of the account that contains the active disclosed address,
including an output at an address `kaspa_accounts` does not return. It does
not select an output of another account, an output spent by an outstanding
submission, or an output that carries a covenant id. When `from` is present,
it selects only outputs at that address, and that address need not be
disclosed. The cases are in
[kcc-0012/vectors/send-selection.json](kcc-0012/vectors/send-selection.json).

### Spendability

An input is spendable by an authorized account when a key of that account
matches the script, whether or not `kaspa_accounts` lists the address. A key
of an account the user did not authorize is code `4100`. A script the account
can satisfy only together with another party is not in the balance set, and
it is spendable for `kaspa_signInputs` and `kaspa_signPskb`.
`kaspa_signMessage` still requires a disclosed address. The cases are in
[kcc-0012/vectors/spendability.json](kcc-0012/vectors/spendability.json).

### Notes and receive addresses

`kaspa_getNotes` returns one element per output in the balance set, ordered
by transaction id then index. Amounts are `Uint64` strings. From the same
view, their sum equals `kas`. The call does not change `kaspa_accounts`.
When the wallet has decoded a KCC-20 state, the note includes `tokenAmount`
and `state`. When the output is P2SH and the wallet can reconstruct the
redeem script, the note includes `redeemScript`. Those fields are public
data.
The first call by an authorized origin prompts and grants the
`kaspa_getNotes` permission. A later call does not prompt until
`wallet_revokePermissions` revokes that permission.
`kaspa_requestReceiveAddress` returns one receive address of the same
account and, when that address was not disclosed, adds it without making it
the first element. The cases are in
[kcc-0012/vectors/notes.json](kcc-0012/vectors/notes.json).

## Security Considerations

**The provider is adversary-controlled.** The provider object lives in the
page, where any script can read, wrap, or overwrite it. A wallet MUST NOT
place private data in the provider. A wallet MUST isolate itself from the
page. A wallet MUST validate every value that it receives from the page. A
wallet SHOULD rate-limit requests. The trust boundary is the wallet's own
user interface, not anything that the page shows.

**Announcements prove presence, not identity.** Any page script can dispatch
`kaspa:announceProvider` with the `name`, `icon`, and `rdns` of another wallet.
A frozen detail only prevents a change to an announcement after dispatch. A
spoofed provider holds no keys and cannot forge a signature. The realistic risk
is display spoofing that leads to a phishing flow. Apps MUST NOT treat `name`,
`icon`, or `rdns` as evidence of anything. Every consent flow happens in the
wallet's own interface.

**Icons.** An SVG icon can contain script. A remote icon leaks the visit of
the user to a third party, and it can change after review. These risks are
the reason for the `data:` URI requirement and the `<img>` rendering rule.

**Origin isolation.** Permissions are keyed by origin. A wallet SHOULD NOT
expose a provider to cross-origin frames unless it attributes each request
to the frame's own origin. A wallet's transport between the page and the
extension MUST verify the origin of every message that it accepts.

**Account exposure.** The exposure of accounts to every page enables tracking
across sites. For this reason, `kaspa_accounts` returns nothing until the
user consents. `kaspa_requestAccounts` exists so that the consent is explicit.

**What an origin may learn about an account.** After the origin holds
`kaspa_accounts`, this interface lets it learn the following.

- The disclosed addresses.
- A further address of an authorized account when the user discloses it, so
  that it appears in `kaspa_accounts`, or when the origin calls
  `kaspa_requestReceiveAddress`.
- Every note of that account, including addresses that are not disclosed,
  when the origin holds `kaspa_getNotes`
  ([Section 6.15](#615-kaspa_getnotes)). That call does not add those
  addresses to `kaspa_accounts`. The first grant prompts. Later calls do
  not, until the permission is revoked.
- That the wallet recognized a script the origin supplied, when a signing
  method prompts, or when the user rejects that prompt with code `4001`.
- The aggregate returned by `kaspa_getBalance`: `kas`, and `tokens` when the
  wallet reports them, with no address breakdown.
- After a transaction is submitted, what the chain makes public.
  `kaspa_sendTransaction` returns only the transaction id. An origin that
  then reads that transaction from a node learns the inputs. This interface
  does not return them.

The origin MUST NOT learn from this interface an extended public key, a
derivation path, a private key, an address of an account the user did not
authorize, or a value that says how many accounts the wallet holds. A fresh
change address of a provider that implements `kaspa_getBalance` is not a
disclosure ([Section 6.5](#65-kaspa_sendtransaction)).

`kas` is not the sum of the disclosed addresses. An origin that reads those
addresses on a public node and compares the sum with `kas` can observe a
difference. When `kas` is larger, the difference is sompi of the same
account at addresses `kaspa_getBalance` did not disclose. The origin learns
that amount from the balance alone. It does not learn the addresses, the
outpoints, or how many outputs make up the difference, unless it holds
`kaspa_getNotes` ([Section 6.15](#615-kaspa_getnotes)). When `kas` is smaller, a disclosed address may
belong to another authorized account, the wallet's view may be behind the
node, or a disclosed output may be outside the balance set
([Section 6.14](#614-kaspa_getbalance)): not accepted, not mature, not yet
allowed by a time lock, or not movable by the account alone. An app MUST NOT
treat that inequality as proof that a second account exists.

`kaspa_signMessage` rejects an undisclosed address and an address of no
authorized account with the same code, `4100`, and it does not prompt
([Section 6.4](#64-kaspa_signmessage)). The `message` MUST NOT distinguish
the two. For `kaspa_signTransaction`, `kaspa_signInputs`, and
`kaspa_sendTransaction` with `from` present, a prompt, or code `4001` after
a prompt, means the wallet recognized the input as an authorized account.
Code `4100` with no prompt means it did not. An origin can probe.
[Section 6.6](#66-kaspa_signtransaction),
[Section 6.7](#67-kaspa_signinputs), and
[Section 6.5](#65-kaspa_sendtransaction) require that the error carry no
address, path, or extended public key. A wallet SHOULD answer repeated
probes with code `-32005`.

`kas` is exact. The wallet MUST NOT add noise to it. Two origins the user
has authorized can correlate the same total until the funds move.
`kaspa_getBalance` does not prompt, so an authorized origin can re-read it.
Code `4100` means the origin is unauthorized or the wallet is locked. `kas`
of `0` means the authorized account's balance set is empty. Those results
differ because one is a refusal and the other is a total.

**Keys stay in the wallet.** The wallet decides whether an output is
spendable by comparing a key it holds with the script
([Section 7.7](#77-signature-scripts),
[Section 6.14](#614-kaspa_getbalance)). It MUST NOT return that key. A
method in this document returns a signature only when the origin called a
signing method and the user approved the call
([Section 5.3](#53-consent)). The other results are disclosed addresses,
amounts, scripts, and, when the origin holds `kaspa_getNotes`, the notes of
[Section 6.15](#615-kaspa_getnotes). `tokenAmount`, `state`, and
`redeemScript` on a note are public data. They MAY contain a public key or
a key hash. A result MUST NOT contain a private key, an extended key, or a
derivation path.

**Session restore.** An app MAY remember a wallet's `rdns` and, after a reload,
call `kaspa_accounts` to redisplay accounts without a prompt. Any page script
can spoof `rdns`. Therefore, an app SHOULD require a fresh explicit selection
of the wallet by the user before it routes a signing request to a provider that
the app did not select in the current page session.

**Blind signing.** The wallet's confirmation for any signing method MUST show
enough for the user to judge the request. For a transaction, this means:

- every output and amount,
- the fee,
- the net change of the balance of each signing account, and
- the payload in full, as hexadecimal and, where it decodes to printable
  text, as text.

A payload can decide where funds go. Bridge deposits that carry the
destination account in the payload are an example. The presence of a payload
alone tells the user nothing. For a message, this means the complete
message. A wallet SHOULD warn when a message or a payload is not printable
text.

When the sighash type is `1`, a signature that `kaspa_signInputs` returns
authorizes the spend of the listed input under the displayed transaction and
nothing else. The wallet SHOULD warn for any other type.

**Message replay.** KIP-5 keys the message hash with a domain that is
separate from the transaction signature hash. Therefore, an attacker cannot
replay a signed message as a transaction signature. This document does not
prevent the replay of a signed message between apps. An app that uses
`kaspa_signMessage` for authentication SHOULD bind the message to its own
domain, a nonce, and an expiry. Ethereum's EIP-4361 shows this pattern.

**Network changes.** Address strings and the spendability of UTXOs depend on
the network. Therefore, a provider MUST keep `kaspa_networkId`,
`networkChanged`, `kaspa_accounts`, and `accountsChanged` consistent at all
times. An app SHOULD discard cached state, including a cached `kas`, on
`networkChanged`.

**Denial of service.** A page can issue requests in a loop. A wallet SHOULD
coalesce or reject duplicate pending prompts with code `-32002`. A wallet
SHOULD rate-limit `kaspa_getBalance` per origin, and MAY rate-limit the
other methods. The code is `-32005`. The wallet MUST NOT prompt when it
applies that limit, and it MUST NOT return a substitute figure in place of
the error ([Section 6.14](#614-kaspa_getbalance)).
